# VK-помощник сообщества аэропорта

Python-бот с SQLite, админкой на FastAPI, импортом базы знаний, GigaChat и очередью сотрудника. Бот выбирает утверждённые ответы; уточнения составляет GigaChat. Изображения обрабатываются отдельно и затем участвуют в выборе карточки.

Оформление админки использует темно-синюю палитру, синие акценты и геометрический мотив потолка терминала. Визуальный ориентир — [айдентика Пулково 2.0](https://www.artlebedev.ru/pulkovo/logo2/). Исходный логотип сохранен без изменений из [публичного SVG авторов](https://img.artlebedev.ru/everything/pulkovo/logo2/pulkovo-logo2-logo.svg) в `pulkovo/static/brand/pulkovo-logo.svg`. В интерфейсе используется только графический знак из него (`pulkovo-mark.svg`), а название набрано общим шрифтом админки по пожеланию пользователя. Эта надпись не является официальной текстовой частью логотипа. Декоративный рисунок интерфейса создан отдельно. Это адаптация для прототипа, а не заявление о соответствии официальному брендбуку. Стили находятся в `pulkovo/static/brand.css`, все ресурсы загружаются локально, без сторонних шрифтов или запросов к сайту аэропорта. Сообщения пассажира сохраняют персиковую заливку, ответы — голубую; ширина окна переписки ограничена 980 px.

## Локальный запуск

```bash
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pulkovo.cli init-config
.venv/bin/python -m pulkovo.cli migrate
.venv/bin/python admin.py
```

Открыть http://127.0.0.1:8080. Пароль — `ADMIN_PASSWORD` в локальном `.env`. `init-config` сохраняет уже существующие значения и генерирует отсутствующие секреты. Файлы `.env`, `.certs/`, `data/` исключены из Git.

Админка запускается отдельно от VK-бота. Для запуска бота:

```bash
.venv/bin/python bot.py
```

Приложение предназначено для одного хоста (macOS/Linux). Четыре обработчика параллельно работают с разными диалогами, сообщения одного диалога идут по порядку. Одновременно разрешён один процесс Long Poll для одной базы.

Вызовы GigaChat сериализованы общей файловой блокировкой бота и админки: у текущего тарифа PERS доступен один поток API. Четыре обработчика не означают четыре одновременных запроса к модели. Ограничение описано в [документации GigaChat](https://developers.sber.ru/docs/ru/gigachat/limitations).

## База знаний

Исходный Excel импортируется один раз; при перезапусках данные остаются в SQLite. Импорт доступен в админке с предпросмотром или командой:

При первом импорте в `data/bot.sqlite3` были созданы 83 черновика (79 основных, 2 для режима «КОВЁР», 2 внутренних контакта), у 13 появились автоматические замечания. Для запуска 7 ноября 2026 года по запросу пользователя опубликованы 70 публичных карточек без таких замечаний; 13 остались черновиками. Актуальные статусы доступны в админке. Если на сервер перенести только код, эта база не переносится: отдельно восстановите резервную копию SQLite или повторите импорт Excel на новом хосте.

```bash
.venv/bin/python -m pulkovo.cli import "/полный/путь/Модерация_обновленный файл.xlsx"
```

Для новых файлов используйте лист «База знаний»: первая строка содержит столбцы «Тема», «Вопрос», «Ответ», далее один вопрос на строку. Необязательные столбцы: «Код», «Другие формулировки», «Условия». Формулы и объединения в этом формате запрещены. Пустой шаблон скачивается из раздела «Импорт Excel». Повторное добавление определяется по коду (уникален для всей базы) или по сочетанию темы и вопроса; переименование файла и перестановка строк не создают дубликатов. Импорт не обновляет существующие карточки.

Для исходного формата заказчика поддержаны листы «Обновл. таблица», «КОВЕР ответы», «Полезные контакты», включая объединённые вопросы. Все записи создаются как черновики; контакты — с внутренней видимостью. Незавершённые и условные ответы отмечаются. Повтор того же файла не создаёт дубли. Изменённый Excel добавляет новые строки, но не перезаписывает существующие карточки: изменения существующих записей проверяются в редакторе. Номер строки служит импортным ключом; перестановка строк в новом файле не является надёжным способом синхронизации.

В карточке сотрудник редактирует вопрос, тему и обычный текст ответа. Дополнительные формулировки и условия применения необязательны и находятся в раскрываемом блоке. Кнопка «Опубликовать» подтверждает готовность ответа; отдельной галочки проверки нет. «Сохранить черновик» / «Снять с публикации» исключает карточку из ответов бота. Черновики, конфликтующие варианты, оставленные на проверку, и внутренние контакты пассажирам не отправляются. Отсутствие автоматических замечаний не подтверждает актуальность правил из исходного Excel. Ссылки для ответов вынесены в справочник. Раздел «Ссылки и контакты» содержит только доступные боту значения с понятными названиями, без настройки видимости. В карточке они выбираются из списка и отображаются обычным текстом. Вставленные вручную URL связываются со справочником при сохранении; технические ключи остаются внутри приложения. Подписанный снимок формы сохраняет связь, если контакт изменили в соседней вкладке. Внутренние записи из Excel остаются в исходном текстовом виде и не создают переменные для ответов. Изменения карточек версионируются, восстановление старой версии создаёт новый черновик. Для полной истории отправки сохраняется фактически подготовленный ответ.

В интерфейсе длинные составные темы исходного Excel показаны короткими названиями: «Багаж и ручная кладь», «Досмотр и контроль», «Парковка и транспорт» и т. д. Соответствия определены в `pulkovo/topics.py`; произвольные новые темы не обрезаются. Одинаковые короткие названия объединяются в фильтрах и статистике, CSV использует те же названия. Исходная тема остаётся в данных для поиска, классификации и истории; сохранение карточки без изменения темы её не переписывает. В редакторах можно выбрать короткую тему из списка или ввести свою.

В редакторе ответа связанные ссылки и контакты выглядят как обычный текст с подчёркиванием. При наведении появляется название из справочника; плашек и отдельной панели действий нет. Общие значения изменяются в разделе «Ссылки и контакты». Внутри редактора сохраняются стабильные ссылки на справочник; одинаковые значения у разных контактов не смешиваются. Обычный текст редактируется рядом со вставками, поддерживаются отмена, копирование и вставка; внешний HTML вставляется как текст. Без JavaScript остаётся обычное текстовое поле. В справочнике для каждого значения можно раскрыть список связанных карточек. Изменение значения применяется при подготовке следующих ответов без повторной публикации карточек; ранее отправленные сообщения остаются неизменными. Контакт связывается с карточкой один раз через список в редакторе; импортированные URL уже связаны автоматически. Защита отправки отменяет подготовленный, но ещё не отправленный ответ, если его данные успели измениться, и передаёт обращение сотруднику.

В админке один пользователь отображается одним диалогом. Вкладки «Нужно ответить», «Ждем пользователя» и «Все диалоги» показывают текущее состояние. История содержит последние 30 сообщений пассажира, бота и сотрудника, новые внизу; полная переписка открывается в VK. Старые ссылки с параметром `ticket` перенаправляются в общий диалог. Внутренние записи передачи сотруднику остаются для учета причин возврата боту, без отдельных карточек и нумерации в интерфейсе. Возвраты в статистике являются событиями, а не количеством пользователей или подтвержденных решений.

Нажатия на кнопки согласия и служебные команды отображаются в переписке по сохранённому действию, даже если текст до согласия не сохранялся или был удалён. Выбор «Согласен» показывается именно как выбор пользователя: устаревшая кнопка сама по себе не подтверждает действующее согласие. История идёт по времени сверху вниз и при открытии прокручена к последним сообщениям. Если сотрудник читает более ранние сообщения, автоматическое обновление сохраняет позицию; к последним можно перейти отдельной кнопкой. Черновик ответа также сохраняется при обновлении.

Для известных ссылок Пулково при импорте и вставке нового URL автоматически подбирается короткое название по адресу: «MAX Пулково», «Telegram Пулково», «Оплата парковки» и т. д. Название вопроса из Excel больше не используется как название ссылки. Для неизвестного адреса исходным названием остаётся URL; сотрудник может изменить его в справочнике. Существующие названия при повторном импорте не перезаписываются.

## Согласие и внешняя обработка

По умолчанию `ALLOW_EXTERNAL_USER_DATA=false`. Доступ к API проверяется отдельно через `check_gigachat.py`; успешная авторизация не подтверждает право передавать персональные данные.

Согласие можно показать целиком в первом сообщении. HTTPS-ссылка на отдельный документ необязательна; если она указана, бот добавит её к тексту. В админке задаются текст, версия и переключатель показа согласия. При изменении текста или ссылки админка автоматически создаёт новую версию. Принятие фиксируется вместе с точным текстом и датой. Ссылка сама по себе не определяет юридическую достаточность согласия: текст и допустимые условия обработки определяет заказчик.

Передача обращений включается через `ALLOW_EXTERNAL_USER_DATA=true` в `.env` и перезапуск бота. Успешный запуск не подтверждает соответствие условиям договора GigaChat. В этом прототипе нет гарантированного обезличивания изображений и текста.

До согласия сохраняются технические идентификаторы входящего события, без содержания сообщения и URL фотографии. После передачи сотруднику новые сообщения сохраняются для общей переписки в админке, даже при отказе от ИИ; в GigaChat они не отправляются. После принятия пользователь отправляет вопрос заново. Отказ переводит к сотруднику. Команда `/отозвать` прекращает новые обращения к ИИ, очищает сохранённые входные тексты и ссылки на вложения. История самого факта согласия сохраняется. Повторный запрос согласия нужен при смене версии документа. Передача сотруднику также отменяет запоздавший ответ модели.

После согласия содержание сообщений сохраняется для работы сотрудника. Срок по умолчанию — 30 дней; метаданные статистики сохраняются отдельно. Очистка: `python -m pulkovo.cli purge` (также выполняется при запуске бота). Для постоянного сервера запускать ежедневно планировщиком. Срок хранения резервных копий и фактов согласия определяет оператор данных.

## Очередь сотрудника

Раздел «Ожидают сотрудника» показывает имя и фамилию из VK, VK ID, ссылку на профиль, тему, причину передачи, время, последнее сохранённое сообщение и статус диалога. Базовые имена профилей кэшируются на сутки и подгружаются фоновым обработчиком; при сбое остаётся ID. Телефон и другие расширенные поля профиля не запрашиваются. Тема хранится в обращении: берётся последняя распознанная тема после завершения предыдущего обращения, а при использовании более раннего сообщения показывается соответствующая пометка. Сотрудник может изменить тему в карточке, в том числе после завершения; ручное значение бот не перезаписывает. Закрытые обращения сохраняют свою тему и превью сообщения в пределах своего периода. Сотрудник берёт обращение в работу и отвечает в поле «Ответ пассажиру» прямо в админке либо в обычном диалоге сообщества VK. После подтверждения отправки диалог автоматически переходит в «Ждём пользователя». Новое входящее сообщение возвращает его в «Нужно ответить», а бот остаётся на паузе. Когда разговор действительно окончен, сотрудник нажимает «Завершить и вернуть боту». Закрытие обращения означает завершение работы сотрудником, а не подтверждение решения пассажиром.

В VK бот пытается установить «важный / неотвеченный». Ошибка метки не теряет обращение: основная очередь находится в SQLite. Поддерживаются личные сообщения, не групповые беседы. Обрабатываются новые события VK `message_reply`: факт ответа сотрудника определяется по `admin_author_id`, собственные ответы бота отбрасываются по `random_id` и метке `payload`. Текст, фотографии и стикеры ответа сотрудника сохраняются в общей истории админки; эти ответы не попадают в контекст ИИ. Фотографии и статические изображения стикеров показываются прямо в переписке. Для остальных вложений показывается тип и ссылка на VK. Отсутствие подписи у вложения не считается потерей текста. Если в событии нет автора, бот запрашивает сообщение через `messages.getByConversationMessageId` (или `messages.getById`). Дополнительно раз в 15 секунд сверяет последние 100 сообщений каждого активного диалога из «Нужно ответить» и «Ждём пользователя», чтобы восстановить пропущенный ответ сотрудника, в том числе после перезапуска. Если в истории уже есть более позднее входящее сообщение, ожидание ответа сотрудника сохраняется. Завершённые во время сверки обращения повторно не открываются. Очередь в браузере проверяет изменения каждые 5 секунд и обновляется автоматически. Неизвестные исходящие без идентификатора сотрудника не закрывают ожидание. После 24 часов без ответа пользователя в статусе «Ждём пользователя» обращение закрывается по неактивности. Бот ничего не отправляет до нового входящего сообщения; новое сообщение остается в том же диалоге. Срок меняется в настройках (0 отключает таймер). Счёт идёт от последнего подтверждённого ответа сотрудника; новые входящие отменяют ожидание, последующий ответ сотрудника начинает новый срок. Сверка с VK выполняется до закрытия, при ошибке VK закрытие откладывается. Неотправленный ответ сотрудника блокирует закрытие. В карточке можно выбрать «Оставить у сотрудника без срока». Причины «Закрыто по неактивности» и «Завершено сотрудником» показываются отдельно в статистике и выгрузке возвратов боту; ни одна не означает подтверждённого решения вопроса. Схема событий: https://github.com/VKCOM/vk-api-schema/blob/master/messages/objects.json . Все сотрудники работают через общий вход администратора. Назначения ответственного нет: диалог находится в режиме бота или сотрудника. Ответы из админки подписаны «Сотрудник» во внутренней истории; пассажиру отправляется только текст ответа.

Ответы из админки проходят через `operator_outbox`: показываются ожидание, отправка, подтверждение и ошибки. У повторов сохраняется `random_id`; повторная отправка одной формы не создаёт дубликат. Если переписка изменилась, введённый текст сохраняется и сотруднику предлагается проверить новые сообщения. После трёх ошибок можно повторить или отменить отправку. Завершить обращение с незавершённой отправкой нельзя. Обновление переписки в браузере сохраняет набираемый ответ и внутреннюю заметку. Отдельная служебная беседа не используется.

После трёх неудачных попыток отправки или отмены подготовленного ответа из-за изменения карточки обращение появляется в очереди. События, уже полученные от VK, сохраняются в SQLite; полное восстановление входящих сообщений за длительное отключение Long Poll пока не реализовано; сверка исходящих ответов сотрудника для открытых обращений работает отдельно.

Постоянная клавиатура после согласия скрывается. Доступны команды `/оператор` и `/отозвать`; старые кнопки также принимаются для совместимости.

## GigaChat и поиск

Технические параметры поиска скрыты из рабочего интерфейса сотрудника и сохраняются при изменении других настроек. Экран проверки показывает выбранный ответ, уточнение или передачу сотруднику без технического JSON.

Базовый режим `full` отправляет все подходящие опубликованные публичные карточки. Сначала проверяется реальный размер через `/tokens/count`: превышение 22000 входных токенов переводит к сотруднику, без молчаливого отсечения каталога. При выборе ответа проверяются ID, публикация, версия и текущий режим. На жалобы — сотрудник; неизвестный вопрос — сотрудник или ограниченное число уточнений. Число «уверенности» модели не используется как доказательство правильности.

`lexical` — простой контрольный поиск. `local` — опциональный локальный multilingual-e5-small с добавлением лексических кандидатов. Для него отдельно установить `requirements-local.txt`; проверьте совместимость PyTorch с Python (текущая среда проекта — Python 3.14). Модель не устанавливается с базовыми зависимостями. При отсутствии ответа после поиска выполняется один повтор по полному каталогу. Качество локальной модели пока не измерено на обращениях аэропорта.

Фотографии: до трёх на сообщение, до 10 МБ каждая; скачивание только с разрешённых доменов VK, уменьшение до 1600 пикселей, удаление метаданных при перекодировании, загрузка в GigaChat и удаление временного файла после обработки. Это не обезличивание. Фотографии как вложенные документы, видео и голосовые сообщения пока передаются сотруднику.

Проверка ответа в админке отправляет в GigaChat только явно подтверждённые сотрудником тестовые данные. Сервис не отправляет тестовые сообщения в VK. Ключи и содержимое переписки не выводятся в консоль.

## Миграции и резервные копии

SQL-файлы находятся в `pulkovo/sql/`; текущая версия `015_session_intro.sql`. Применённые версии, даты и SHA-256 находятся в `schema_migrations`. Каждая новая миграция выполняется в отдельной транзакции; при ошибке откатывается. Изменять применённые файлы нельзя — создавайте следующий файл с новым номером. Миграции применяются при открытии базы либо командой `python -m pulkovo.cli migrate`.

Перед обновлением существующей версионированной базы создаётся резервная копия через SQLite Backup API в `data/backups/`. Для сложного изменения таблицы в новой миграции создайте новую таблицу, перенесите данные, удалите старую и переименуйте новую с учётом внешних ключей. Инструмент исполняет только завершённые SQL-выражения, по одному выражению на строку или блоку; не включайте собственные BEGIN/COMMIT. Автоматических downgrade-миграций нет: восстановление из копии проводится при остановленных боте и админке.

```bash
.venv/bin/python -m pulkovo.cli backup data/backups/manual.sqlite3
```

Не копируйте только основной файл работающей WAL-базы: используйте Backup API. Все процессы должны работать с файлом на локальном диске одного хоста.

## Проверка качества

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -s tests -v
```

Для сравнения стратегий используйте JSONL с полями `id`, `text`, `expected_action` и `expected_title` (точное название опубликованной карточки или null). В тестах должны быть обезличенные обращения с ручной разметкой, отдельные от примеров для настройки. Без `--live` измеряется попадание карточки в кандидаты; с `--live` добавляется фактический выбор GigaChat и расход токенов. Пример формата: `tests/fixtures/evaluation.example.jsonl`. Это вымышленные примеры, не готовая оценка качества на данных аэропорта.

```bash
.venv/bin/python -m pulkovo.cli evaluate tests/fixtures/evaluation.example.jsonl --strategy full
.venv/bin/python -m pulkovo.cli evaluate tests/fixtures/evaluation.example.jsonl --strategy lexical --live
```

Статистика считает входящие сообщения, успешные содержательные автоответы, уточнения, передачи и ошибки доставки раздельно. Показатель «Автоматизация ответов» равен доле отправленных готовых ответов без передачи сотруднику среди таких ответов и фактических передач. Для одного входящего сообщения передача имеет приоритет над отправленным ответом: оно не попадает в обе группы. Повторные передачи того же сообщения, согласия, благодарности, промежуточные уточнения и последующая переписка сотрудника знаменатель не увеличивают. При отсутствии результатов отображается прочерк. Новый запрос к сотруднику после ответа считается отдельным результатом; связь между повторными вопросами не устанавливается. Поэтому показатель описывает автоматизацию обработки, а не подтвержденное решение вопроса. Период определяется по дате входящего сообщения с итоговым результатом; закрытие по неактивности не считается успешным ответом бота. Согласие и подтверждение передачи сотруднику не считаются содержательными ответами. Время обработки включает поиск и вызовы ИИ, но не ожидание в очереди. Стоимость в рублях не вычисляется без выбранного тарифа.

## Сервер

Админка работает на FastAPI и Uvicorn. Команда `.venv/bin/python admin.py` запускает ее по адресу `http://127.0.0.1:8080`; другой порт задается переменной `ADMIN_PORT`. HTML-интерфейс использует Jinja2, данные хранятся в SQLite. Бот запускается отдельным процессом: `.venv/bin/python bot.py`.

На VPS запускайте ASGI-приложение командой `.venv/bin/uvicorn admin:app --host 127.0.0.1 --port 8080` под менеджером процессов и открывайте админку через HTTPS reverse proxy с защищенным доступом. Миграции выполняйте до запуска процессов. Копии БД и секреты храните вне публичных каталогов. Реальная отправка и кнопки VK требуют проверки в тестовом сообществе; импорт приложения и запуск админки не запускают бота.

Вход защищен паролем, ограничением попыток и подписанной cookie на 8 часов с HttpOnly и SameSite=Strict. Изменяющие формы требуют CSRF-код. Размер загрузки ограничен 11 МиБ. После перехода с Flask нужно один раз войти заново: старые cookie не используются. Схема SQLite и ранее сохраненные данные при переносе не меняются. Обработчики SQLite, Excel и GigaChat выполняются в пуле потоков, чтобы ожидание синхронных операций не блокировало цикл ASGI.


Короткие благодарности («Спасибо», «Большое спасибо», «Благодарю») распознаются локальным правилом и получают «Пожалуйста! 🙂» без вызова GigaChat. Сообщения с новым вопросом или проблемой проходят обычную обработку. В режиме сотрудника бот не вмешивается. Более сложную благодарность также может распознать GigaChat. Благодарности учитываются отдельно от готовых ответов и не подтверждают решение вопроса.

Отдельные приветствия («Привет», «Здравствуйте», «Добрый день») после согласия получают короткое приветствие с предложением задать вопрос или отправить фотографию без обращения к ИИ. Новому пользователю сначала показывается согласие. Приветствие с вопросом или вложением проходит обычную обработку. Автоответ не отправляется во время работы сотрудника или ручного ограничения; подготовленное приветствие отменяется при смене режима. Приветствия не увеличивают автоматизацию ответов и не запускают опрос оценки. В проверке ответа админки используется то же правило.

Отдельные прощания («Пока», «👋 до свидания», «До встречи», «Спасибо, до свидания») получают ответ «До свидания! 👋» без вызова ИИ. Прощание не засчитывается как решенный вопрос, не вызывает сотрудника и не создает опрос само по себе. После готового ответа уже запланированный опрос остается и отправляется через 60 минут тишины после прощания. Прощание сбрасывает контекст уточнений; сессия завершается по прежним правилам: после оценки или 24 часов бездействия. Фразы вроде «Пока не могу найти багаж», вопросы и сообщения с фотографиями проходят обычную обработку. Во время работы сотрудника бот не вмешивается.

Команды для передачи сотруднику: `/оператор`, `оператор`, `сотрудник`, `связаться с сотрудником`. Их нужно отправить отдельным сообщением; регистр букв не важен. Явную просьбу о человеке в свободной форме также может распознать GigaChat. Кнопка «Написать сотруднику» переводит диалог сотруднику без согласия на ИИ. `/отозвать` и «отозвать согласие» только отзывают согласие и предлагают выбрать способ общения.

Если бот или сотрудник уже отвечал пассажиру за последние 24 часа, из начала следующего готового ответа, уточнения, приветствия или уведомления о передаче удаляется отдельная вводная фраза вроде «Здравствуйте!». Остальной текст и сама карточка не изменяются. Это правило учитывает доставленные сообщения независимо от короткого контекста ИИ, благодарности и смены режима диалога. После 24 часов без ответов приветствие снова допустимо. Проверка ответа в админке показывает вариант для начала нового разговора. Проверка актуальности карточки перед отправкой допускает только это изменение приветствия; изменение ссылки или содержательной части по-прежнему отменяет подготовленный ответ.

Для фото без подписи и контекста GigaChat сначала формулирует уточняющий вопрос по видимым деталям. Фото с понятной подписью может сразу получить готовый ответ, в том числе при недовольстве пользователя. Описания изображений сохраняются вместе с запросом и передаются при продолжении разговора, затем удаляются по сроку хранения или отзыву согласия. При достижении настроенного предела уточнений и при ошибке API остается передача сотруднику.

## Ответы до передачи сотруднику

Жалоба или негативный тон сами по себе не вызывают передачу. Бот выбирает применимый опубликованный ответ, уточняет неоднозначный вопрос и зовет сотрудника при просьбе о человеке, необходимости реального действия, отсутствии ответа или не помогшем ответе без альтернативы. Вопрос, куда отправить отзыв об уборке, может получить карточку, а просьба прислать уборщицу требует сотрудника. Общая форма обратной связи не заменяет ответ о причинах или правилах.

Миграция `010_complaint_answers.sql` снимает прежнее автоматическое действие «Передать сотруднику» у импортированных публичных карточек раздела «Жалобы», если оно никогда не менялось в истории. Создаются версия и запись аудита; тексты и публикация сохраняются. Будущие импорты также не назначают передачу по названию темы. Карточки остаются черновиками до проверки. Вручную указанное действие `handoff` по-прежнему обязательно.

Модель возвращает ID, название и цитату выбранной карточки. Приложение сверяет их соответствие, не считая пробелы и пунктуацию изменением смысла цитаты. Пассажиру отправляется исходный опубликованный текст. При некорректном результате возможна одна попытка исправления; затем передача сотруднику. Отсутствие аналитических меток у корректной передачи не стирает ее причину; неизвестный тон не подменяется нейтральным. Для продолжения разговора передаются до четырех последних пар вопросов и ответов за 30 минут в текущем режиме бота. Благодарность и изменение режима очищают этот контекст. При ограниченном поиске отсутствие ответа проверяется по полному каталогу. Проверка в админке использует те же правила выбора карточек.

Известные ошибки можно повторно проверить командой `evaluate` с `tests/fixtures/routing.regression.jsonl`. Это синтетические проверки на конкретных опубликованных карточках, а не независимая оценка качества на новых обращениях.

## Окно диалога для сотрудника

Ссылки на диалоги открывают отдельное окно с контрастной синей шапкой поверх очереди или обзора. «Свернуть» убирает окно в кнопку с именем пассажира в правом нижнем углу. Нажатие на нее или на того же пассажира в очереди возвращает переписку, черновик и место чтения. Новые события в свернутом чате отмечаются на кнопке. «Закрыть» завершает работу с окном; при несохраненном тексте появляется предупреждение. Такой же контроль защищает черновик при открытии другого пассажира.

Без JavaScript доступна обычная страница диалога. История обновляется, не стирая черновик и не сбрасывая место чтения. Очередь не перезагружает страницу, пока чат открыт или свернут. Черновик хранится только в текущей странице, не переносится в хранилище браузера. При уходе со страницы с черновиком браузер предупреждает о потере несохраненных данных.

- «Ответить вместо бота» включает режим сотрудника и останавливает автоответы в диалоге. Сообщение пассажиру не отправляется. Отдельного назначения ответственного нет.
- «Отправить ответ» ставит сообщение в очередь VK от имени сообщества. После подтвержденной отправки статус меняется на «Ждем пользователя».
- «Завершить и включить бота» завершает работу сотрудника. Бот обрабатывает только последующие новые сообщения; старые ожидающие задания не запускаются заново. При неотправленном ответе или временном ограничении автоответов возврат запрещен с пояснением.
- «Автоматический возврат боту» управляет ожиданием после ответа сотрудника. Отсутствие ответа пассажира не считается подтверждением решения вопроса.

Переключение режима проверяет версию диалога в одной транзакции. Устаревшая форма не может закрыть новый вопрос или перебить действие коллеги. Тема, заметка, ожидание и защита вынесены в раскрывающиеся разделы.

## Защита обработки сообщений

Миграция `011_message_protection.sql` добавляет состояние временного ограничения и счетчики. Миграции применяются при следующем запуске с автоматической резервной копией. Перед обновлением остановите оба процесса.

- Входящий поток ограничен емкостью 12 сообщений на пользователя с восстановлением за минуту. Служебные команды имеют отдельную емкость 6 за минуту. В очереди допускаются до пяти необработанных сообщений пользователя и до 200 суммарно; уведомление о лимите может добавить одну запись. При общей заполненной очереди новые задания не создаются. Отзыв согласия применяется до этого ограничения.
- Перед дорогой обработкой резервируется доступ к ИИ: емкость 30 обращений пользователя и 300 обращений сообщества с восстановлением за час. Используются сохраняемые в SQLite token buckets: разрешен короткий всплеск в пределах емкости, затем доступ восстанавливается постепенно. Это ограничения обращений, не точный денежный бюджет или число HTTP-вызовов. Одно обращение может включать до трех изображений и повторную проверку ответа.
- Лишние сообщения не создают бесконечную историю или новые обращения сотруднику. Сохраняются агрегированные счетчики причин; уведомление о срабатывании отправляется не чаще раза в минуту пользователю. Сообщения остаются в обычной переписке VK. Счетчики переживают перезапуск и очищаются по сроку хранения. Срабатывания не считаются успешными ответами в автоматизации.
- В разделе «Спам и ограничения» сотрудник может отключить автоответы и ИИ на 24 часа и снять ограничение раньше. Опросы отменяются, подготовленные автоответы отменяются, общение сотрудника и отзыв согласия остаются доступными. Снятие ограничения не забирает диалог у сотрудника. Пока ограничение активно, автоматическое закрытие по неактивности не включает бота.
- Простые явные попытки изменить системные инструкции обрабатываются локально без ИИ. Ругательства, недовольство и сообщения о мошенничестве сами по себе не блокируются. В инструкциях ИИ текст пассажира, подпись и надписи на фото считаются данными. У модели нет инструментов исполнения кода, изменения базы или самостоятельной отправки сообщений.
- Готовые ответы берутся из опубликованных карточек. Свободно сформированные уточнения проверяются по длине, формату, ссылкам и типовым опасным запросам: пароли, платежные данные, коды подтверждения, установка программ и команды оболочки. Фильтр не заменяет проверку качества базы сотрудником.
- Изображения принимаются только по HTTPS с разрешенных доменов VK, без учетных данных в URL, нестандартных портов и переходов по перенаправлениям. Ограничены объем, разрешение и длительность загрузки; согласие повторно проверяется при чтении потока. Файл декодируется и заново сохраняется как JPEG перед обработкой.

Эти меры уменьшают риск злоупотреблений, но не дают гарантии распознавания мошенника или всех вариантов prompt injection. Закодированные и новые атаки могут обходить текстовые фильтры; срабатывание не является доказательством мошенничества. Для публичного сервера дополнительно нужны HTTPS, защита доступа к админке и ограничения на reverse proxy. Подход к разделению данных и инструкций и ограничению ресурсов основан на рекомендациях [OWASP по prompt injection](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) и [защите от отказа в обслуживании](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html).


В статистике доступны «Сегодня», «Вчера», «24 часа», «7 дней», «30 дней» и произвольные даты включительно (до 365 дней). По умолчанию показан текущий день. Календарные границы и группировка по дням определяются в часовом поясе Europe/Moscow; «24 часа» является скользящим интервалом. Для 7 и 30 дней текущий день включен. Таблица показывает долю автоматизации, число ответов бота и передач сотруднику за каждый день, включая дни без результатов. Итоговый процент взвешен по количеству результатов, а не усреднен из дневных процентов. Таблица доступна в CSV; выгрузки сообщений и возвратов из страницы используют выбранные границы. Старые ссылки с `days` сохраняют прежний расчет скользящего периода.

## Оценки помощи бота

После отправленного готового ответа бот через 60 минут тишины предлагает оценить помощь: «Как вы оцениваете помощь бота?» с пятью кнопками «1 ⭐», «2 ⭐», «3 ⭐», «4 ⭐», «5 ⭐» прямо под сообщением. Шкала поясняется в тексте: 1 — совсем не помог, 5 — полностью помог. Это текстовые кнопки VK: нажатие отправляет выбранную подпись и служебные данные опроса. Новое сообщение пассажира и последующий ответ бота начинают отсчет заново. «Спасибо» после готового ответа тоже переносит опрос, но благодарность сама по себе опрос не создает. При ожидании уточнения, передаче сотруднику, ответе сотрудника или отзыве согласия опрос отменяется. Возврат управления боту не возобновляет старый опрос: нужен новый готовый ответ.

Не более одного приглашения пользователю за 24 часа, без напоминаний. Проверка очереди выполняется каждые 15 секунд. Перед отправкой сверяется свежая история VK: пропущенное входящее сообщение откладывает опрос, ответ сотрудника или неизвестное исходящее после ответа бота отменяет его. Ошибка чтения истории откладывает отправку. При сбое отправки используются до трех технических попыток с одним `random_id` и проверкой истории, чтобы не создавать дубликаты. Неопределенный результат отправки также учитывается в суточном ограничении. Приглашения старше 24 часов с последней активности не отправляются после простоя.

Кнопка сохраняет первую оценку конкретного опроса; повторное нажатие ее не меняет. На сохраненную оценку бот отвечает «Спасибо за оценку!». Для этого GigaChat не вызывается. Оценки не создают новые обращения и не меняют режим управления диалогом. Оценка текущей консультации завершает ее сессию. Поздняя оценка после нового вопроса или передачи сотруднику не завершает текущую работу. Оценки 1–2 сохраняются для разбора, без автоматического перевода сотруднику. Опрос и нажатая кнопка видны в истории админки.

В разделе «Статистика» показаны средний балл из 5, распределение по звездам, доля оценок 4–5 среди ответивших и доля ответивших среди отправленных опросов со звездами. Средний балл считается по всем оценкам выбранного периода, а не как среднее дневных показателей. Данные доступны по дням и в CSV. В статистику, CSV и список низких оценок входят только опросы со звездами. Прежние опросы «Хорошо / Плохо» и поздние ответы на них не учитываются в отчетах; сохраненные данные и история переписки остаются в базе. Используется выбранный период по дате отправки опроса; поздние оценки обновляют день первоначального приглашения. Отсутствие оценки не является положительным ответом. Для последних десяти оценок 1–2 доступны ссылка на диалог, вопрос и сохраненный ответ бота перед опросом; сама оценка может относиться ко всей консультации. Содержание удаляется по общему сроку хранения, числовая статистика остается. Опросы и оценки не увеличивают показатель автоматизации ответов.

Переключатель «Просить оценить помощь бота» находится в настройках и по умолчанию включен. Отключение отменяет запланированные опросы. Миграция `009_feedback_surveys.sql` добавляет отдельную таблицу; старые диалоги не опрашиваются задним числом. После обновления опросы планируются только для новых доставленных ответов. Перед миграцией остановите бот и админку, затем запустите оба процесса с обновленным кодом. Ожидание и оценки хранятся в SQLite и переживают перезапуск.

Миграция `014_feedback_stars.sql` добавляет шкалу опроса и числовую оценку 1–5. Запланированные опросы без попыток отправки переходят на звезды. Уже отправленные опросы и опросы с неопределенным результатом отправки сохраняют прежние текст, кнопки и токены, чтобы поздние нажатия и повторы отправки работали корректно. Для каждого опроса принимается только оценка его шкалы. CSV содержит только опросы и оценки со звездами.


## Начало общения и текстовое согласие

Встроенное приветствие при первом открытии диалога задается в VK: «Управление → Сообщения → Приветствие». Код бота эту настройку не изменяет. Текст для поля: «Здравствуйте! Я бот Пулково ✈ Помогу узнать о рейсах, багаже, парковке и услугах аэропорта. Просто напишите свой вопрос — постараюсь помочь!». Приветствие VK не повторяется при каждом открытии существующей переписки. Первое сообщение пассажира запускает обычную проверку согласия в боте.

В первом обращении нового пользователя приветствие показывает VK, а бот отправляет только условия обработки данных и способы согласиться. После согласия бот подтверждает его сохранение и предлагает написать вопрос или прислать фотографию, без повторного приветствия. В следующих сессиях приветствие добавляется к первому ответу бота. Уведомление по умолчанию кратко описывает обработку сообщений и фотографий для ответа, хранение переписки и доступ сотрудников. Названия технологии и провайдера в нем не указаны. Это текст интерфейса прототипа, юридическую форму согласия определяет заказчик. В админке отдельно показаны первый ответ новому пользователю и приветствие следующих сессий. Исходные карточки базы знаний не меняются.

Отдельные сообщения «Согласен» и «Согласна» принимаются локально, без GigaChat, только после успешно отправленных актуальных условий за последние 24 часа. Смешанная фраза, отрицание, вложение или сообщение во время работы сотрудника не дают согласия. До согласия содержание вопроса не сохраняется и в ИИ не передается. Бот сохраняет версию, показанное сообщение и факт текстового подтверждения. При изменении условий нужно новое подтверждение. Администратор редактирует условия в настройках; инструкция о согласии добавляется автоматически.

## Сессии внутри диалога

Один пользователь остается одной строкой в очереди. Новые сообщения объединяются в сессию. В переписке видны начало, завершение и причина завершения; при показе последних 30 сообщений сохраняется заголовок продолжающейся сессии. Старые сообщения без идентификатора сессии остаются общей историей, без выдуманных границ.

- Первая оценка актуальной консультации закрывает сессию с причиной «После оценки». Низкая оценка также завершает ее, но не считается успехом и не вызывает автоматическую передачу сотруднику.
- Поздняя оценка после нового вопроса сохраняется для старого опроса и не закрывает новую работу. Благодарность после опроса не мешает завершить ту же консультацию оценкой.
- Без оценки сессия бота закрывается через 24 часа после последнего сообщения пассажира или доставленного ответа бота. Приглашение оценить через 60 минут и служебное подтверждение оценки не продлевают срок. Незавершенная обработка или отправка блокирует закрытие.
- Следующий вопрос начинает новую сессию с пустым контекстом ИИ. Старое согласие сохраняется, если его условия не изменились. В первом ответе новой сессии снова появляется вступление, даже если с момента оценки прошло меньше суток.
- При передаче сотруднику сессия продолжается. Ее закрывает ручное завершение или существующий таймер статуса «Ждем пользователя». Открытый вопрос, на который сотрудник еще не ответил, и отключенный автоматический возврат не закрываются таймером бота.

Проверка срока выполняется каждые 15 секунд при работающем боте и перед приемом нового сообщения. После простоя записывается фактическая граница 24 часов. Закрытие не отправляет пассажиру отдельное уведомление. В статистике есть число завершений по каждой причине за выбранный период. Формула автоматизации ответов не меняется: завершение сессии не является подтверждением решения вопроса.

Обновление: остановить бот и админку, выполнить `.venv/bin/python -m pulkovo.cli migrate`, затем запустить оба процесса. Перед миграцией автоматически создается резервная копия существующей базы. Сессии, сроки и оценки переживают перезапуск.

## Рейсы по онлайн-табло Пулково

Подключен бесплатный источник, которым пользуется сам сайт: `https://pulkovoairport.ru/api/?type=arrival&when=0` и аналогичный запрос с `type=departure`. Адрес найден в скрипте официального табло, формат и загрузка через Python проверены 22.11.2026. Это внутренний публичный источник сайта, без обещания стабильного формата или доступности. Платный авиационный сервис не используется.

Примеры сообщений: «SU 25 сегодня», «Когда прилетит рейс DP 894 завтра?», «Какой гейт у SU 25 сегодня?». Номер нужен с латинским кодом авиакомпании. Дата относится к расписанию в Пулково по московскому времени. Поддерживаются «вчера», «сегодня», «завтра», «послезавтра», ДД.ММ, ДД.ММ.ГГГГ и даты словами, например «22 ноября». Для даты за пределами четырех дней бот объясняет ограничение табло. Если указан только номер, уточняет дату; ответ «завтра» продолжает поиск. Контекст рейса хранится в SQLite, действует до 30 минут внутри текущей сессии и поколения управления, прекращается при смене темы. Новый номер не наследует дату предыдущего рейса.

Поиск по городу: «Какой ближайший рейс в Красноярск», «Рейсы из Москвы завтра», «Ближайший прилет из Нижнего Новгорода». «В город» означает вылет из Пулково, «из города» означает прилет в Пулково. Если направление не указано, бот уточняет его. Для обычного списка без даты бот спрашивает дату. Запрос ближайшего рейса без даты проверяет доступное окно от вчера до послезавтра, включая задержанные со вчерашнего дня рейсы.

Ближайшие рейсы сортируются по ожидаемому времени, а при его отсутствии по расписанию. Отмененные, уже вылетевшие/прибывшие и отправленные со стоянки рейсы исключаются из поиска ближайших. Задержанные без нового времени и рейсы с прошедшим временем без подтверждения отправления показываются отдельно: в этом случае бот не утверждает, что однозначно определил ближайший рейс. При запросе списка за конкретный день видны и завершенные или отмененные рейсы с их статусами. Ответ содержит до трех рейсов, даты и время по Москве, статус, аэропорт и ссылку на табло. Если совпадений больше, бот сообщает их количество.

Названия городов сопоставляются с данными табло целиком; похожие названия не подменяются. Поддерживаются распространенные падежи, отдельные формы составных названий и аэропорты Москвы. «Москва» охватывает все московские аэропорты на табло; «Москва SVO» или «Шереметьево» ограничивают поиск. Слова «а завтра?» и «а в Москву?» продолжают текущий поиск. Для выхода, стоек или багажной ленты нужно выбрать номер рейса и дату. Если часть дат недоступна, бот показывает найденные данные с пометкой о неполноте, не подтверждает ближайший рейс и не засчитывает результат как решенный вопрос. Ни отсутствие совпадений, ни недоступность табло сами по себе не переводят диалог сотруднику.

Сообщения «другой рейс», «новый рейс» и «еще один рейс» начинают новый поиск без GigaChat: предыдущие номер, дата и направление сбрасываются. Бот просит номер другого рейса и дату; их можно отправить вместе или по очереди. Если новые данные уже указаны в сообщении, они сохраняются. Вопросы о переоформлении билета на другой рейс продолжают обрабатываться по базе знаний.

Распознавание явного запроса, поиск и ответ выполняются без GigaChat, расход токенов равен нулю. Текст пассажира и ID VK на сайт аэропорта не передаются: загружается общий список за день, поиск идет локально. Неоднозначные номера не подменяются похожими; совместные номера рейса учитываются. При совпадениях в прилете и вылете бот уточняет направление. Совпадения в одном направлении предлагается проверить на табло. Вопросы о возврате билетов, компенсациях, нормах багажа и других правилах остаются в прежнем поиске по базе знаний. Свободный поиск по городу, распознавание номера на фотографии и подписка на изменения рейса пока не реализованы.

В ответе показаны маршрут, авиакомпания и текущий статус. При задержке сначала выводятся «Рейс задержан» и ожидаемое время, затем отдельно «По расписанию было». Если новое время отсутствует или источник оставил прежнее, бот сообщает, что новое время пока не указано. Для прибывшего или вылетевшего рейса показывается фактическое время; одинаковые ожидаемое время и расписание не дублируются. Для вылета добавляются выход на посадку и стойки регистрации, для прилета багажная лента. Если значения нет, это указано прямо. Время после полуночи сопровождается датой. Все значения показаны по Москве; время отправления со стоянки отличается от фактического вылета. Для отмененного рейса выходы и стойки не выводятся. Время обновления источника и проверки ботом пассажиру не показывается, проверка свежести продолжает работать внутри приложения. Бот сообщает текущее значение выхода, но не утверждает, что его перенесли: история изменений пока не ведется.

Общий кеш на процесс обновляется по запросу не чаще раза в минуту для направления и даты. Все четыре рабочих потока используют один кеш. Ошибка также кешируется на минуту, чтобы не повторять запрос при каждом сообщении. При перезапуске кеш создается заново. Время `TimeStamp` проверяется у всех строк: данные старше 10 минут или с некорректным временем не выдаются как актуальные. Пустой, поврежденный ответ, HTTP 403, перенаправление и таймаут дают понятное сообщение и ссылки на табло. Старые данные не используются в качестве запасного ответа. Ответ, простоявший в очереди отправки больше срока кеша, заново проверяется перед отправкой в VK.

Сетевые запросы ограничены по времени и размеру (2 МБ), отправляются только на фиксированный адрес сайта с проверкой HTTPS через системное хранилище сертификатов (`truststore`). Глобальные настройки TLS для VK и GigaChat не меняются. На сервере должен быть установлен актуальный пакет корневых сертификатов ОС. При недоступности сайта с IP сервера бот корректно сообщает об этом, без обхода защиты сайта.

Согласие, защита от частых сообщений и приоритет сотрудника продолжают действовать. Успешно отправленный ответ по рейсу учитывается в автоматизации и может запустить обычный запрос оценки через 60 минут тишины. Уточнения, отсутствие рейса и недоступность источника не считаются решенными вопросами и не запускают оценку. Результат и тема «Рейсы» видны в админке. В разделе «Проверка ответа» можно проверить тот же сценарий без отправки в VK. Данные табло не попадают в историю, отправляемую GigaChat для других вопросов.

Для обновления остановите бот и админку, установите зависимости (`.venv/bin/python -m pip install -r requirements.txt`), выполните `.venv/bin/python -m pulkovo.cli migrate` и запустите оба процесса. Миграция `013_flights.sql` добавляет контекст рейса и срок актуальности ответа, существующая база автоматически резервируется. Новые ключи API и настройки `.env` не нужны. Проверка модуля: `.venv/bin/python -m unittest discover -s tests -p 'test_flight*.py'`.

Сообщение в начале сессии редактируется в настройках. В первой сессии нового пользователя оно не добавляется, поскольку приветствие уже настроено в VK. Для вернувшегося пользователя оно добавляется к первому содержательному ответу, уточнению, сообщению о передаче сотруднику или запросу согласия, в том числе когда пассажир сразу задает вопрос. Возвращение определяется по предыдущим сессиям или ранее принятому согласию; просмотр приветствия VK через API не запрашивается. Вступление и ответ отправляются одним сообщением. В продолжающейся сессии вступление не повторяется; отдельные оценки, благодарности и прощания его не запускают. Миграция `015_session_intro.sql` сохраняет использованное вступление в записи ответа: повтор отправки остается неизменным, проверка актуальности карточек и ссылок сохраняется. В контекст ИИ добавляется ответ без вступления.

После запуска и восстановления связи бот сверяет пропущенные оценки по последним 100 сообщениям в VK для неоцененных опросов за срок хранения, максимум 30 дней. Один диалог проверяется не чаще раза в минуту, до 10 диалогов за цикл. Принимаются только кнопки с токеном отправленного опроса этого пользователя; текстовые числа оценками не считаются. Восстановленное нажатие появляется в истории и статистике без повторной отправки благодарности. Старые вопросы не запускаются заново, более новая работа сотрудника или пассажира не закрывается. Это восстановление оценок, а не полная синхронизация всей переписки после отключения.
